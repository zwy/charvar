# 验收、证据与交付检查

## 1. 证据字段

以下为逻辑字段，可以放在 Markdown 表格里，不要求开发 JSON／YAML 存储系统。

| 字段 | 取值 | 含义 |
|---|---|---|
| execution_status | unknown / not_run / user_reported_run | 用户是否实际执行了本轮生成 |
| user_approval | unknown / proposal / result / partial / rejected | 用户认可的对象与强度 |
| assistant_image_review | not_seen / reviewed | 助手是否实际看到结果图 |
| batch_validation | not_tested / recorded | 是否有多次运行记录 |
| feedback_quote | 自由文本 | 用户反馈原话 |
| approval_scope | 自由文本 | 本轮认可的目标或局部 |

**这些字段独立，不是自动升级链。** 看图不代表满意；用户认可不代表助手看图；单次满意不代表批量稳定。

旧标签 proposed、user_reported、image_reviewed、batch_tested 保留为显示摘要使用，但必须能还原到上述细分字段，不单独作为结论。

### 判定示例

| 用户消息与上下文 | 应记录 |
|---|---|
| 生图测试轮次：「不错，继续」 | execution_status=user_reported_run；user_approval=result；assistant_image_review 另记 |
| 「图片生成了，不错」 | 已运行；结果认可 |
| 「提示词看着不错，我晚上跑」 | not_run；proposal |
| 「衣服行，脸不行」 | 已运行；partial（衣服）／脸待修 |
| 「还没跑，先下一步」 | not_run；按要求跳过并记未测 |
| Skill 讨论中：「不错，按这个方案改」 | 方案／实施确认，不产生生图测试证据 |
| 上传结果图但没表达满意 | 可检查图像（assistant_image_review=reviewed），不自动写 user_approval=result |

### 旧记录兼容

不批量把历史「不错」全部升级。只在原对话语境或用户补充足以支持时修正。核心原文缺失时，标为明确标注的重建稿，并说明正式交付缺口，不编造为「原文」。

## 2. 设计与证据来源

每个关键属性可以标记：图中可见／用户要求／设计补全／已核验外部事实／尚未确定。补全经用户认可后可以成为角色设定，但不能改写成原图本来如此。
没有看到生成结果图时不编造鼻形、接缝、手指等实际偏差。推测原因标「可能」，不要写成诊断结论。

## 3. 每轮三至五项验收

- 身份：头部、脸或物种特征是否同一主体。
- 形态：身体、附肢、比例与重心是否合理。
- 造型：配色、服装层次、装饰位置和材质是否延续。
- 本轮目标：景别、视角、接触关系、表情或背景是否达成。
- 媒介：人物、道具、环境是否采用一致表现。

按当前阶段删减，不要求半身图展示鞋，不要求严格侧面同时展示双眼，不要求被遮挡标记强行露出。

## 4. 提示词静态检查

- 输入图存在、引用职责明确、平台引用统一。
- 身份保留与服装／姿势／背景替换不冲突。
- 固定前缀不混入某一次场景默认动作（固定表情、姿态、灰底、镜头）。
- 正常与精简的核心特征一致，完整示例不重复叠加前缀。
- 没有未替换的场景占位符；模板本身允许保留占位符，但应标为不可直接提交。
- 正文不依赖用户手动拼接未展开模块。
- 参考说明、道具、限制等计入完整提交字符数。
- 不将名字、抽象质量词或长负向清单替代具体结构。

**完整提交稿与内部组件要有明确区分。** 建议约定「完整提交稿」与「内部组件」的标识，或继续使用显式选择的 `text` 代码块。不要不加区分地把所有 `text` 围栏都当作生图提示词。

## 5. 交付完整性检查

**两项基础图必须有明确位置。** 在交付模板与最终文档中，全身正面定妆与同图设定板各自有独立、可定位的条目（提示词原文、输入职责、状态）。缺任何一项都不算正式交付。

**不存在互相冲突的旧正式交付条件。** 同一仓库内不同时保留「至少一个视角变化或跨场景认可」与「两项基础图获认可」两套门槛。旧条件必须被删除或明确标记为已废止。

**主文档自包含检查。**

- 两项基础图的获认可提示词**精确原文**内嵌在主文档中，不靠外部文件引用。
- 若主文档推荐额外「已认可示例」，该示例同样内嵌精确原文。
- 不存在「设定同上一轮」「见对话」「提示词在 prompt_r2.md」这类外部依赖而不含必要内容。
- 不要求安装本技能才能读懂角色资产。
- 不假装文档本身包含了没有嵌入或附带的图片。
- 不把文档索引 R1／R2 当作平台素材 ID。

**双模式检查。** 固定角色与用户照片扮演是两个独立入口，身份来源、允许变化、禁止混用项分别写清，测试状态不共享。用户照片不被强行套上固定角色的五官或体型。

### 5.1 交付文档只写当前态

交付文档是**资产**，不是开发流水账。判断标准跟 AGENTS.md 一样：**只写现在是什么，不写怎么变成这样的。**

| 属于交付 | 不属于交付（留在开发侧） |
|---|---|
| 识别锚点表（属性｜设定｜来源） | 版本号、更新日期、版本记录表 |
| 固定前缀（身份锁，全文只出现一次） | 证据台账：反馈原话、批次、seed、助手是否看图 |
| 基准图场景段（不含身份描述） | 「已验证的写法经验」类案例总结 |
| 槽位表与各槽位状态 | 编号错乱的「已知问题」堆叠 |
| 已知限制（当前仍成立且影响使用的事实） | 外部路径引用与「见上一轮」式指代 |
| 用户照片扮演的职责边界 | 身份描述的重复副本 |

**机器查得到的**用 `scripts/check_delivery.py` 查：篇幅、章节齐全、身份是否只写一次、版本历史残留、
外部依赖、围栏角色、声明字数。

**只能人工核的**：

- 已知限制写的是当前仍成立的事实，不是历史问题清单。
- 「未测试」项没有在别处被当成已验证。
- 场景段确实没有复述固定前缀里的身份细节（机器只能查逐字重复，查不了换了说法重述）。
- 固定前缀里的内容确实是本角色的身份，不是上一轮遗留的别人设定。
- 一个主体只有一套默认服装，没有并列的第二套。
- 固定前缀是**逐锚点成句、以名词开头**的，不是分号串起的一整段——分号长句在
  `subject derive` 抽取时只取第一个子句，后面的锚点会整段丢失。

## 6. 案例经验的泛化限制

案例成功写法只能写成案例记录或优先尝试方案，不升级为模型通用规律。

| 可以写 | 不可以写 |
|---|---|
| 本案例分节重写后，用户反馈布局满意 | 不分节模型就不会执行版式任务 |
| 初始布局试用 35%／65% | 所有角色必须使用 35%／65% |
| 本次使用单一半身参考得到满意结果 | 所有全身设定板只需要半身参考，不需要任何下身设定 |

## 7. 字符预算与脚本边界

预算由本次任务提供，或取目标平台明示的字符上限（即梦 2000 字符是当前项目默认值 —— 带参考图的 image2image；纯文生图 text2image 上限约 1600 字符 —— 由用户提供，不包装成平台的永久官方承诺）。上限是硬边界，超出即无法提交。优先预留场景空间，而不是让固定前缀独占总预算。正常版无需强行达到某字数，精简版不能删掉身份关键结构。

脚本按 Python `len` 统计 Unicode 码点，包含空格和换行；Markdown 代码围栏不计入选取的 text 代码块。它不是模型 token 计数，也不保证等于平台计数。

脚本对 `{{...}}` 和 `【全局固定前缀】` 等仅做粗略检查，可能漏报或误报；必须人工检查语义、设定一致性和图片表现。指定严格总预算时，最终可提交示例应通过；超限示例应压缩或明确注明所需更大预算，不标成合规。

**不提供固定等价倍率。** 英文与中文之间不套用通用换算系数，也不由字符长度推出费用。直接实际计数。若保留经验估算，必须标明样本范围、仅供估算，不作计费依据或硬门槛。详见 [语言、长度与字符预算](length-and-language.md)。

## 8. 实测原文与整理版

保存 submitted_prompt 的精确文本；测试后不就地润色覆盖。另建 compiled_prompt 并记录来源版本、变化与「待复测」。正常版、精简版分别记录证据，不能互相借用通过状态。
没有模型参数时记未提供，不补造种子、批次或成功率。

## 9. 交付检查清单

1. 用户是否请求交付，而非只讨论。
2. 全身正面基准与同图设定板是否都已获用户认可（或已有等效认可资产）。
3. 两项基础图的完整提示词原文是否可在主文档内直接取得。
4. 角色特征、风格、服装、场景与输入模式是否分离。
5. 已认可、提案、缺失与待测内容是否清楚；未测试能力是否被误写成已验证。
6. 原文、整理版、精简版是否可追溯。
7. 字符统计是否实际执行，完整提交稿的计数是否完整。
8. 是否存在互相冲突的旧正式交付条件。
9. 文件是否存在、非空，包内引用是否有效。
10. 是否误宣称已自动安装 Skill、保存用户本地文件或写入外部仓库。

# 角色开发与提示词资产化 Skill｜使用说明

版本：1.0.0  
日期：2026-10-25

## 这是什么

一个分阶段的人机协作技能包。它帮助 AI 在新角色建立、参考图提取、缺失设计补全、换风格、全身定妆、同图多视角、跨场景和角色资产文档交付之间正确推进，并保留反馈与基准。

它不是自动生图程序，不含模型服务、收费 API 或批量生产系统。包内字符脚本仅做文本辅助检查，不评判视觉质量。通用 Skill 核心不携带缇珞的固定人设。

## 最短路线

```text template
S0 任务与边界
  ↓
S1 全身正面定妆（必做）                    ← 用户实际出图并认可
  ↓
S3 同图半身＋正侧背全身设定板（必做，最核心） ← 用户实际出图并认可
  ↓
S5 自包含 Markdown 资产交付
```

S2 身份细化（头肩／半身）与 S4 跨场景默认可选，不为流程完整机械追加。独立头肩图、独立侧面图、独立背面图等辅助分图完成后，核心设定板仍标记未完成，不能被分图替代。

已有满足要求且获用户认可的资产可以直接复用，不必重新生成。

## 包内内容

- SKILL.md：带 name 与 description 元数据的核心入口。
- references/：阶段与路由、输入模式与基准职责、验收与证据、语言长度与字符预算。
- templates/：项目状态、轮次回复、提示词记录（可选深度记录）与最终角色资产文档模板。
- examples/：缇珞插画与真人路线案例，不是默认角色配置。
- scripts/prompt_budget.py：Python 标准库字符统计和粗粒度占位符检查。
- tests/：本地静态检查脚本与测试夹具。
- manifest.json：版本、文件清单与检查结果记录。

核心约定：用户未要求落地时不提前创建文件；实际测试原文不被整理版覆盖；只得到用户文字认可时不假装看过结果图；风格分支与角色实例分开管理；用户执行、用户认可、助手看图、批量测试分别记录。

## 两种使用方式

### A. 放入普通项目或聊天上下文

提供 SKILL.md 及当前需要的引用文件，或把解压后的文件加入支持读取文件的项目中。先确认当前 AI 能读取这些文件；仅上传 ZIP 并不保证宿主会自动解压或加载。

如果宿主不能读取相对引用，就手动提供相应 workflow、input-modes、quality-checks 文件。它可以作为普通 Markdown 规范使用，不要求专门的 Skill 加载器。

### B. 使用支持技能目录的工具

按具体工具的官方说明，将 character-forge 目录放到它要求的技能位置，并确认该工具识别入口与相对文件。当前包使用通用 SKILL.md 入口组织，不宣称已完成某个具体客户端的适配、安装或自动激活；不同宿主的目录与支持能力应单独确认。

在 charvar 仓库里，这个技能由 `scripts/install_cli.sh` 装到 `~/.claude/skills/character-forge`（软链），
仓库内另有 `.claude/skills/character-forge` 软链，Claude Desktop 聊天面另有一份复制件。

## 第一次这样开始

```text template
请按《角色开发与提示词资产化》Skill协作。
这是一个新角色项目，我会提供参考图和可选原提示词。
先判断已有信息与需要补全的设计，输出第一轮可复制提示词。
一次只解决一个主要问题，我反馈认可后再推进。
这次先不要生成最终角色文档。
```

继续已有项目：

```text template
按同一Skill继续。请先读取项目状态和对应提示词记录。
当前风格分支与基准图见我提供的附件。
不要重做已经认可的部分，按当前未解决项推进。
```

换风格：

```text template
为这个已确认角色建立一个新的真人摄影分支。
保留角色识别与服装设计，转换媒介和必要比例。
旧分支保留，先做单人全身，不一次性生成全部流程。
```

用户照片扮演：

```text template
我想让自己的照片来演这个角色。
终端输入是我自己的一张照片，服装和场景按这个角色的设定来。
请说明哪些保留、哪些需要转换，先给一条完整待测提示词。
```

正式整理：

```text template
当前方向已认可，请按Skill整理角色资产文档。
保留已测试提示词的精确原文，整理版另行标注。
固定角色延续和用户照片扮演是两个独立入口，分别标注状态。
未测试扩展不要写成已验证。
```

## 两个使用模式

同一份角色资产提供两个**独立**入口：

| 模式 | 身份来源 | 终端输入 | 主要边界 |
|---|---|---|---|
| A 固定角色延续 | 获认可的基准图 | 认可基准图 | 不重新设计脸或体态 |
| B 用户照片扮演 | 上传者自己的照片 | 单张照片 | 不套固定角色脸、眼色或体型 |

抖音引用为「素材1」，视频号为「#图1」。两种模式的测试状态分别标注，不互相借用；未实测的入口不写成已验证。

## 主文档定位

正式交付是**一份自包含 Markdown**，默认标题「角色提示词资产文档」。文档内嵌角色设定与设计补全、双模式职责、两项基础图的获认可提示词精确原文、基准图的实际状态与取得方式、待测范围，以及给新 Agent 的接手说明。

不依赖未随附的开发记录目录，不使用「见对话」「提示词在别处」这类外部引用，不假装文档包含没有嵌入的图片。开发记录（项目状态、提示词记录）是可选的深度记录。

## 项目数据放哪里

templates 是空白表单，不是当前项目状态。为每个实际角色复制项目状态与提示词记录，保存在用户自己选择的位置。角色实例与 Skill 规则分开，避免以后换角色还带入旧设定。

建议记录最少四样：当前阶段、实际基准图、精确提示词、用户反馈。缺图时写“未归档”，不编造路径。

## 字符检查脚本

需要 Python 3，只有标准库依赖。在解压后的技能目录执行：

```bash
python3 scripts/prompt_budget.py my-prompt.txt --budget 2000 --strict
python3 scripts/prompt_budget.py templates/character-document.md --markdown --budget 2000
python3 scripts/prompt_budget.py my-prompt.txt --budget 2000 --strict --language en
```

- 普通模式统计整个文件，包含空格和换行；保存文件时的末尾换行也会计入。
- Markdown 模式统计每个 text 代码块，排除围栏及围栏分隔换行。
- CRLF 或 CR 换行统一为 LF；按 Python len 统计，不是模型 token。
- --strict 遇到超预算或粗略占位符候选返回 1；无此参数只报告。
- --language en 额外输出等效中文字符数估计，仅供估算参考，不作计费依据或硬门槛。
- 正常运行返回 0；读取或用法错误返回 2。
- 模板中的占位符本来就需要保留，不能把模板检查报告当作交付失败。
- 占位符检查有局限；脚本不核验身份、服装一致性、矛盾、图片质量、授权或平台真实限制。

## 本地检查

```bash
python3 tests/run_checks.py
```

> 在 charvar 仓库里，这个脚本已被仓库级门禁接住（`tests/test_skills.py` 会调起它），
> 交付前跑 `python3 -m pytest -q` 即可，不必单独记着跑。单独跑它主要用于调试。

覆盖可自动化的部分：Python 语法、Markdown 内部链接、占位符与超预算判定、交付模板中两项基础图的位置、是否残留互相冲突的旧交付条件、错误的字符换算与计费表述是否已清除、证据字段与双模式入口是否在文档中、文件存在且非空、示例资产中标注的字符数是否与实际测量一致、manifest 与实际文件是否一致、三处版本号是否同步。

全部通过返回 0，有失败返回 1。夹具在 `tests/fixtures/`，均为明确标注的虚构内容。

加 `--record` 会把这次真实运行的结果写回 `manifest.json`：

```bash
python3 tests/run_checks.py --record
```

`manifest.json` 记录版本、文件清单与检查结果。检查结果只在实际运行时写入，不预填。

**脚本查不了的**：同一服装配件在档案与提示词中是否一致、正常版与精简版是否真的没有互相矛盾、证据措辞是否被夸大、双模式是否被混用、设定板四描绘是否真的同一角色。这些仍是人工核对项。

## 语言与字符上限

- 提示词语言跟随用户本轮的沟通语言：中文沟通用中文提示词，其他语言沟通用英文提示词。
- 平台字符上限是硬边界，超出即无法提交。即梦 2000 字符是当前项目默认值，由用户提供，不是平台的永久官方承诺。其他平台未指定时明确写出预算来源。
- 计数按 Python len 的 Unicode 码点，包含正文空格与换行，不含 Markdown 围栏与围栏外说明。字符数、token 数与价格不互相换算。
- 英文超限时的压缩顺序见 `references/length-and-language.md`。

## 代码块角色

Markdown 里的 `text` 围栏带一个角色标记，用来区分「可以直接提交的提示词」和「不是提示词的文字」：

| 写法 | 含义 | 参与预算检查 | 占位符算失败 |
|---|---|---|---|
| ` ```text submit ` | 完整可提交提示词 | 是 | 是 |
| ` ```text component ` | 内部组件，需与其他段组合 | 否 | 否 |
| ` ```text template ` | 模板占位符，本就待替换 | 否 | 否 |

没有角色标记的 ` ```text ` 块按 `submit` 处理。这样预算检查不会把组合说明或内部模块误当成一条提示词。

## 反馈与证据

在明确的生图测试轮次中，用户回复「不错，继续」默认表示已经实际生成并认可本轮结果，除非上下文明确只是方案认可或尚未执行。讨论 Skill、讨论方案、确认交付时不套用该默认值。

四项分别记录，不互相推导：用户是否执行、用户认可什么、助手是否看到图、是否做过多次测试。没收到图片写「用户侧已生成，尚未提供给助手」，不写「未产生」；不要求用户为每轮反馈上传结果图。

## V1.2 不强制覆盖

双主体与视频只保留扩展入口，不纳入必跑路线。不接入外部平台，不自动执行生成或覆盖既有角色文件。

## 可验收的核心行为

1. “先讨论”时不创建文档。
2. 生图测试中的“不错，继续”记为已运行＋结果认可；讨论中的“不错”不产生生图证据。
3. 未看图不等于没执行；用户认可不等于助手看图，也不等于批量稳定。
4. “衣服好，脸不行”只修脸，锁定衣服。
5. 辅助分图完成后核心设定板仍未完成，不能宣布核心板已完成。
6. 已有认可资产直接复用，不从头重做。
7. 两项基础图获认可即可正式交付，不强制跨场景或两种模式都实测。
8. 换风格另建分支，认可新图后用新分支延续。
9. 角色名和案例属性不污染新项目。
10. 资产化后保留原文、整理版、长度与待测边界，两项基础图原文内嵌主文档。
11. 提示词语言跟随用户沟通语言，交付前用 --strict 校验实际平台上限。
12. 不把字符数当费用，不提供中英等价倍率当硬规则。

## 迁移说明

从 1.1.0 升级时，旧的「至少一个视角变化或跨场景认可即算正式交付」门槛不再适用，改用两项基础图获认可。旧的四标签证据写法仍可作为显示摘要，但需要能还原到四项细分字段。历史案例文档不重写为符合新规则的样子；新版只改技能本身。
